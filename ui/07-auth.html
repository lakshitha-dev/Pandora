Why this screen exists at allWith a password form the session is created by the same request that submits it. With OAuth the browser comes back from Google carrying a code that still has to be exchanged. That exchange can fail on its own, so it needs a screen — otherwise the user stares at a blank page and refreshes, which consumes the single-use code and guarantees the failure.

Sign-in cancelled

No account was created and nothing was shared.

⊘
You closed the Google window before finishing, or chose not to continue.

Or use the console without an account.

Cancelling is not an errorAmber, not coral, and it says plainly that nothing was created or shared. A user who backed out deliberately should not be shown a failure — and the reassurance about data matters more on an OAuth screen than a password one, because the user just saw a permissions prompt.

The two failures worth distinguishing

state · provider error

Couldn't complete sign-in

Google returned an error before a session was created.

✕
Google declined the request. This usually means the redirect URL isn't on the provider's allow-list.
error=redirect_uri_mismatch · state ok · no session created

If this keeps happening it's a configuration problem, not something you can fix by retrying.

Show the provider's error codeOAuth failures are almost always configuration — a redirect URI that doesn't match, or a consent screen not published. Surfacing redirect_uri_mismatch turns a twenty-minute hunt into a ten-second fix, and it is not sensitive: it names our own callback URL back to us.
state · network / exchange failed

Couldn't reach the server

Google confirmed you, but we couldn't finish on our side.

⚠
The code exchange didn't complete. Your Google account is fine and nothing was changed. Check the connection and start again.

Retrying restarts the whole flow — the previous code is single-use and has already been spent.

Different from a provider errorThe user did nothing wrong and Google did nothing wrong, so it is amber and it explicitly reassures them about their Google account. It also warns that retry restarts the flow rather than resuming it, which prevents the refresh-the-callback loop that burns the code.

Why clearance is picked here, not in the consoleRole is not a display preference — it filters what retrieval is allowed to return, under POL-005. A Citizen is not cleared for healer-limited clinical detail. That has to be resolved before the first query, so it belongs on the way in rather than in a settings page nobody opens.
Each option states its clearance explicitlyShowing public only against Citizen means a user who later sees "2 sources withheld" already understands why. Hiding the mapping would make the withheld notice feel like a malfunction.
Only on first sign-inReturning users go straight to the console with their stored clearance. A returning-user prompt is a step that can fail in a demo for no benefit.
Auth stays off the critical pathSOLUTION.md §12 keeps it there deliberately, and the idle screen offers "continue without signing in" for exactly that reason. A login wall between a judge and the console is pure downside — Google OAuth needs network, a published consent screen, and a matching redirect URI, none of which are guaranteed in a judging room.

The one configuration trapThe redirect URI must be allow-listed for every origin you sign in from. A build that works on localhost:3000 and fails on the deployed URL is almost always this, and it surfaces as redirect_uri_mismatch — which is why that error code is shown to the user rather than swallowed.
